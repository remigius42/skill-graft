# Design

## Context

ADR 0006 and the **Check** entry in `CONTEXT.md` settle the boundary: the agent advises, skill-graft resolves.
What the skill can lean on already exists:

- `build --into <folder>` vendors into `<folder>/.apm/skills/<name>/` and writes `<folder>/skill-graft.lock`, the
  bytes an in-place build would write, never runs APM, and leaves the **Package** byte-identical. It prints
  `skill-graft: package: <path>`, then `skill-graft: into: <absolute folder>`. The folder must exist and be empty,
  and must not lie in a **Package**, a path **Source**'s folder or the git cache; `build` never creates or deletes
  it, and a failed build leaves it empty.
- A git **Source** may set `subdirectory`; the lock's `upstream` stays relative to the repository's root, so it
  includes the `subdirectory`.
- The lock (`version = 1`) lists each **Hull** **Skill** with `deployed`, `upstream` (relative to the git repository's
  root or the path **Source**'s folder) and `patches`, and each edge with its kind and `bind`. `skill-graft why <id>`
  prints the absolute **Upstream** folder.
- `add`, `bind` and `unbind` refuse any edit that does not resolve and then write nothing. The unmatched-reference
  warning and the ambiguity error already suggest `skill-graft bind`.
- No command writes **Patches**; the README's "Writing a patch" recipe does it with `cp`, `diff` and `git apply`.
- A git **Source** with no `ref` loads; `skill-graft update <alias>` sets it.

## Goals / Non-Goals

**Goals:**

- A skill whose every finding ends in config the user accepted, through the commands that check it.
- One deterministic guard in pytest: the shipped skill resolves alone, with no warnings, so its own text never
  becomes a defect it would report.

**Non-Goals:**

- Stale **Patches** after `update`.
- Any new CLI output (JSON, near-miss lists); the agent reads the text itself.

## Decisions

- **Ships as a plain skill folder, not Python package data.** It is fetched as a git **Source** like any other,
  so its **Ref** moves with `update` and the CLI never special-cases it. Alternative: the CLI installs it. Rejected:
  a second install path, and the skill would no longer be built by skill-graft itself.
- **`skills/graft-check/`, installed with `subdirectory = "skills"`.** `.claude/` is generated by `openspec init`
  and holds six tracked `openspec-*` skills. A **Source** of the whole repository would make them candidates for
  the user's cross-**Source** **References**: a `/openspec-explore` elsewhere would pull in this repository's copy,
  or turn ambiguous. The `subdirectory` key of the `source-subdirectory` change, which lands first, keeps
  discovery to `skills/`.
- **Its text names no skill but itself.** A slash or Skill tool name resolves in every **Source**, so even one a user's
  other **Source** holds would grow the **Hull**. Examples in it use placeholders, not `/tmp` or real names, so its
  **Hull** stays itself alone; its own name, in its usage line, is no **Reference**, since the walk drops
  self-references. The pytest guard commits a copy of the working tree's `skills/` into a temporary git repository and
  declares it as a git **Source** with `subdirectory = "skills"`, as the template installs it: discovery confines a git
  **Source** to its commit, which a path **Source** would not, and the working tree means a `SKILL.md` not yet staged
  counts, test-first and without `.git`.
- **Upstream folders: one `why` per git Source.** A path **Source**'s folder is in the lock (`sources.<alias>.path`,
  in project scope relative to the **Package**). A git **Source**'s `upstream` is relative to a cache export the
  skill cannot locate portably: `why` prints one **Skill**'s absolute folder, and minus the lock's relative
  `upstream` that gives the root for all its **Skills**. Each `why` resolves the whole config, so once per git
  **Source**, never per **Skill**.
- **A patched Skill's hunks are read, not applied.** `why` and the lock's `upstream` name the folder before any
  **Patch**. The rewrite and link kinds compare it with the vendored copy, so the skill reads the lock's `patches`
  for that **Skill** and counts the lines they change as intended. Applying them would take `cp`, `git apply` and
  writes, tools a read-only look should not need.
- **Fixes go through the CLI wherever one exists.** `add`, `bind` and `unbind` already refuse what does not
  resolve, patches applied, so a rebuild after them fails only while vendoring (an unreadable file, a path **Source**
  edited meanwhile). The skill still undoes any failed fix, a cheap safeguard: `remove` after `add`, the noted value
  after `bind` or `unbind`, and for a **Patch** its file, its own list item, and the key and the `[patches]` table
  only when the skill created them.
- **A Bind is source-wide, so it is checked against the text.** Before proposing `bind <alias>/<name> false` or a
  redirect, the skill searches the **Upstream** text of that **Source**'s **Hull** **Skills**, plus the lines their
  **Patches** add, for the name in each **Reference** form. The lock's edges cannot answer this: they hold targets, not
  the names written, and a `false` **Bind** leaves no edge. If some uses are right, a **Patch** of the **Skill** with
  the wrong one fits instead. Every rebuild is diffed against the previous lock's **Skills**, so a fix that drops one
  says so.
- **The README recipe, with the real Package.** The recipe spells out the user **Package**; the skill puts the
  `package:` line's path in its place, so project scope writes its own `patches/`.
- **Every build goes `--into` a new temporary folder, made with `mktemp -d`.** Looking must not change the
  **Package**: a committed project **Package** would show a dirty tree, and the user could not just look. `--into`
  needs an existing, empty folder and never creates one, so the skill runs `mktemp -d` first, as its own command
  (not `--into "$(mktemp -d)"`, which a `Bash(skill-graft:*)` permission does not cover), then passes the path.
  A new folder per build, since a used one is not empty; successive locks are what the hull comparison diffs.
  The folders are left to the system's temporary-folder cleanup, so the skill needs no delete permission.
- **The `skill-graft build` advice when a build would change something, judged by the vendored folders.** `add`,
  `remove`, `rename`, `bind`, `unbind`, `update` and `resolve` write the **Package**'s lock without vendoring, so
  a lock can be current while `.apm/skills/` is behind; comparing locks would miss exactly the `ref` the user
  moved. The skill compares the throwaway `.apm/skills/` with the **Package**'s (`diff -rq`); any difference, or
  an accepted fix, earns the advice. Whether APM deployed what the **Package** holds stays unknowable locally, so
  otherwise the skill says so instead of advising a build it cannot justify.
- **Only version 1 is read.** It is the first lock version, so no lock can be older. The update advice names no alias:
  the checked **Package** may not be the one that installed `graft-check` (a user-scope install checking a project), so
  it points the user at the **Source** they installed it from, in that **Package**.
- **One subagent per checked Skill**, each reporting findings of the per-skill kinds (missed, false, rewrite, link) in a
  fixed shape; the main agent judges wrong targets, merges, and proposes. `skill-graft tree` gives the targets; it shows
  one edge per target, kind and **Bind**, and a prose edge only when rewritten, so the agent judges every use of each
  target's own name and of each `[bind]` key bound to it (the lock's edges hold targets only). Without subagents, the
  main agent goes through the **Skills** one by one.
- **Template block is a commented `[sources.skill-graft]`** with `subdirectory = "skills"`, plus the three commands to
  run (`update`, `add`, `build`), not an `entries` line: the template's example `entries` line is already there, and
  `add` writes the **Entry** once `update` has set the `ref`. The block says that until then every `build` fails, not
  only graft-check's, since a git **Source** without a `ref` blocks the whole **Package**.
- **Eval, not test, for the agent.** `evals/graft-check/run.sh` builds a project **Package** in a temporary folder (a
  git **Source** made with `git init` and committed with `GIT_AUTHOR_*` and `GIT_COMMITTER_*` set, since the temporary
  `HOME` has no git identity; no network), one per named scenario (`run.sh [scenario…]`, all by default): planted
  defects with a user **Patch**, a clean **Package** built or never built, a scoped run, an argument that is no **Skill
  ID**, a failing build, a lock the `skill-graft` wrapper rewrites to `version = 2`, and a second `claude -p --continue`
  turn that accepts one fix. It runs `claude -p` there, then greps each report: a finding counts when one line holds its
  text and its kind. Left to manual review, since a headless run cannot reliably make a build fail mid-fix or accept a
  given `add`: One false match among real calls, A skill joins the hull, Bind restored, Earlier patches kept, Source
  changed, and Lock current, vendored copies behind. A project **Package** is found before the user's, so the real
  `~/.apm` is never read or written.
  - `HOME` and `XDG_CACHE_HOME` point into the temporary folder, as AGENTS.md asks of anything that runs `apm`,
    though nothing here does: the real `~/.claude` and `~/.cache/skill-graft` stay untouched, the user's
    settings, hooks and personal skills (a deployed `graft-check` among them) cannot change the run, and the
    working copy in the project's `.claude/skills/` is the only `graft-check`. With no `~/.claude` login to read,
    `claude` takes its credentials from the environment: `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`,
    billed to the subscription) or `ANTHROPIC_API_KEY`. The script needs one of them and, with neither, stops
    before building anything, pointing to `claude setup-token`.
  - `--allowedTools` grants `Bash(skill-graft:*)`, `Bash(mktemp:*)`, `Bash(diff:*)`, file reads and searches, and
    subagents; headless, any other tool call is denied, not asked. `TMPDIR` also points into the temporary folder, apart
    from the eval **Package** and `XDG_CACHE_HOME`, since `--into` refuses a folder in a **Package** or the cache (and
    in a path **Source**, such as the eval's `art`). `--add-dir` grants the whole temporary folder:
    the throwaway builds, the cache and the sources lie outside the project, where reads and `diff` would be denied.

## Risks / Trade-offs

- The agent misses a defect or invents one → it only proposes; every fix needs the user's yes and passes the
  CLI's checks.
- The lock layout changes under the same `version` → a new `resolve` requirement and a test pin the version 1
  keys, failing with a reminder to raise `version`; the skill stops on a version it does not know.
- The eval costs tokens and varies between runs → opt-in and run by hand when the skill changes.
